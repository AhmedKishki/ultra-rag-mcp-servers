# memory-rag: a standalone memory app with a command center

Status: in progress. Four decisions settled by the user on 2026-10-01; everything else follows
`research-rag`, which is the shape a product in this collection takes.

## The four decisions

1. **The process model is one app, not one app per project.** A command center is the central
   place to manage *all* global and project local memory. That is one process holding the
   account's global memory plus the local memory of every registered project, on one loopback
   port. This is the one place `memory-rag` deliberately departs from `research-rag`, which is
   one process per project, because memory has an account-wide scope that a per-project process
   would have to attach separately and a browser would have to visit in turn.
2. **`memory-ultra-rag-mcp-server` is frozen, and keeps its submodule and repository.** Three
   copies of it are running on this machine right now, two of them on `ai-and-fetishism`, and
   all three share one 40 KB global memory. It reads and writes the same `.memory-rag/` and
   `<storage-root>/memory/default/` layout this app uses, so the on-disk contract is frozen on
   both sides for as long as both ship. This is the treatment `research-ultra-rag-mcp-server`
   got, for the same reason.
3. **The MCP surface is the four memory tools, unchanged.** `record_memory`, `recall_memory`,
   `forget_memory`, `record_handoff`. The app adds no agent-only power: the four are the whole
   of what an agent may do to a memory, and the command center holds everything else.
4. **The UI's SQL panel reads freely and writes statements only.** `SELECT` and schema
   inspection are unrestricted. `INSERT`, `UPDATE` and `DELETE` are allowed on the `unit` table
   and nothing else, and every accepted write rebuilds the FTS5 word index, re-renders
   `MEMORY.md`, and drops the affected vectors so they are embedded again. `DDL`, `PRAGMA`,
   `ATTACH`, writes to `meta` and writes to `vector` are refused by name.

## Why the SQL panel is shaped that way

`memory.sqlite3` is not a derived cache. It holds the statements, the kind each is filed under,
its stamp, its date, its recall count, the word index, and the vectors, and it is the record.
Deleting it costs a re-read, a re-embedding, and the counts. So an unrestricted SQL panel is a
`DROP TABLE` away from a memory nothing can read back, and the recovery path is retyping every
statement from `MEMORY.md`, which is a rendering this app writes and does not read back.

The write rule keeps the one property the store depends on: a statement in the table is a
statement the index and the vectors agree about. A hand edit that went around that would leave
the word index and the vector table describing a statement that is no longer there, which is a
memory that answers wrongly rather than one that fails loudly.

## Architecture

```text
MCP client ── HTTP /mcp ─┐
                       │
stdio client ── bridge ──┤
                       ├── memory-rag (one process, one port, one account lock)
Browser workspace ─ HTTP ┤      │
                       │      ├── MemoryService
Terminal ── control ───┘      ├── registry: every project this install serves
                              ├── scope policy: global + one local per project
                              ├── store, index, retrieval, reranking, models
                              ├── sql console (statements only, then reindex)
                              └── shared workspace (surfaces/ui.py)
```

The engine is the memory server's code, unchanged. Everything that changes is above it.

## Package layout

```text
src/memory_rag/
  app.py          the running app: port, workspace, /mcp, client registry
  control.py      the loopback control API the CLI speaks
  bridge.py       `memory-rag mcp`: stdio to the app's /mcp
  registry.py     the projects one installation knows about
  launcher.py     port claim, pid, port file, log, generated launcher
  service.py      MemoryService: the one implementation
  <engine>        config, settings, store, index, vectors, read, retrieval,
                  maintenance, reindex, models, instructions, sql
  surfaces/
    cli.py        the command centre
    mcp.py        the four tools and the instructions
    ui.py         the workspace profile, the adapter, and the SQL panel adapter
```

## Commands

| Command | Effect |
|---|---|
| `init` | record the project identity, create `.memory-rag/`, write the launcher |
| `projects` | list every project this install serves |
| `start`, `ui`, `serve`, `stop`, `status` | the app's lifecycle |
| `recall`, `record`, `forget`, `handoff` | the four memory operations, through the running app |
| `scopes` | the global memory and every project's local memory, with their sizes |
| `sql` | run SQL against a scope, then reindex when it wrote |
| `reindex` | rebuild the word index and re-embed pending statements |
| `export` | write the `MEMORY.md` rendering |
| `config`, `doctor` | local reads, in process, never starting the app |
| `clients`, `disconnect` | the attached MCP clients |
| `mcp` | the stdio bridge |
| `help` | the grouped menu and its subject pages |

## Data roots that keep their names

The account settings directory, the `MEMORY_ULTRARAG_*` environment prefix, the model cache, and
the scope directory names stay as they are while the frozen server ships, because a rename
strands every existing memory and forces a silent model re-download. `tests/test_data_roots.py`
states each one and why, exactly as it does in `research-rag`.

## Rules

- The engine imports neither Starlette nor FastMCP, no engine module imports a surface, and no
  surface imports another. `tests/test_architecture.py` enforces it.
- One capability, one implementation. The workspace, the agent surface and the command line
  cannot disagree, and the SQL panel is the only way to write a statement that is not a tool
  call, so it is bounded rather than a second writer.
- The four tools are the only agent surface. The command center holds every other operation.
- The on-disk contract is frozen while `memory-ultra-rag-mcp-server` is installed.
- A project's local memory never leaves its repository, and the global memory is one per account
  with no user dimension.
